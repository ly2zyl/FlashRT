# Pi0.5 Houmo HMM compatibility adapter

> This adapter is not the native FlashRT M50 port. It consumes an existing
> Dadao HMM graph bundle and exists only as a compatibility/reference path.
> `m50_xh2` remains reserved for a source-checkpoint build owned by FlashRT.

FlashRT's M50 backend executes Dadao-compiled HMM graphs through
`tcim_lite`. It preserves the public FlashRT VLA API while replacing CUDA
kernel composition and CUDA Graph capture with an XH2 static-graph bundle.

## Runtime boundary

```text
FlashRT VLAModel API
  -> Pi05M50Frontend (pre/post-processing and scheduling)
  -> tcim_lite
  -> Dadao HMM static graphs
  -> M50/XH2
```

M50 does not execute CUDA kernels or safetensors directly. The HMM files are
the M50 device kernels and must match the installed Dadao runtime, driver, and
firmware release.

## Environment checks

Run inside a Houmo Dadao deployment container with the M50 device mapped in:

```bash
hm_smi

python3 - <<'PY'
import tcim_lite as tcim
print(tcim.runtime.get_device_num("Xh2HalBackend"))
PY
```

The Python check must print at least `1`. Install FlashRT without building its
CUDA extensions; the M50 frontend does not import them:

```bash
cd /workspace/FlashRT
python3 -m pip install -e ".[m50]" --no-build-isolation
```

The environment also needs `torch`, `transformers`, `safetensors`, and the
`tcim_lite` package supplied by Dadao.

Keep the deployment isolated in a virtual environment under `icode`. The
provided launcher defaults to `/workspace/icode/.venv-m50-runtime` (the
sibling of the two source directories) and deliberately does not fall back to
the system interpreter. Set `FLASHRT_VENV` when the mount point differs.

On this machine, create or refresh that environment with:

```bash
cd /home/sky/icode/robot_assistant_release_20260509
./create_flashrt_m50_venv.sh
```

The script writes only the new virtualenv and the editable FlashRT checkout.
It inherits the already installed M50 `torch` and `tcim_lite` packages from
`yolo11m-hm` read-only; it does not install into or modify that environment.

Run the bundled diagnostic before loading the graphs:

```bash
python3 examples/m50/pi05_doctor.py \
  --checkpoint /workspace/robot_assistant/models/pi05_libero_finetuned \
  --compiled-model-dir /workspace/robot_assistant/outputs/pi05/xh2 \

```

## One-shot inference

```bash
cd /workspace/FlashRT

python3 examples/m50/pi05_smoke.py \
  --checkpoint /workspace/robot_assistant/models/pi05_libero_finetuned \
  --compiled-model-dir /workspace/robot_assistant/outputs/pi05/xh2 \
  --tokenizer /workspace/robot_assistant/models/paligemma-3b-pt-224 \
  --image /path/to/base.png \
  --image /path/to/wrist.png \
  --prompt 'put the bowl on the stove' \
  --state 0 0 0 0 0 0 0 0
```

Programmatic use:

```python
import flash_rt

model = flash_rt.load_model(
    checkpoint="/models/pi05_libero_finetuned",
    config="pi05",
    framework="torch",
    hardware="m50_hmm_compat",
    compiled_model_dir="/models/pi05/xh2",
    tokenizer_path="/models/paligemma-3b-pt-224",
    device_id=0,
)

actions = model.predict(
    images=[base_rgb, wrist_rgb],
    prompt="put the bowl on the stove",
    state=raw_robot_state,
)
```

For the M50 frontend, `state` is the raw physical robot state. The frontend
reads `normalization_mapping` from `config.json`, applies the matching
`MEAN_STD`, `MIN_MAX`, `QUANTILES`, `QUANTILE10`, or `IDENTITY` transform,
pads the result to 32 values, and encodes it in the OpenPI state-prompt
format. Returned actions are inverse-transformed using the same checkpoint
configuration and postprocessor statistics.

## LIBERO robot loop

The local robot-assistant checkout contains a FlashRT adapter and selects it
by default:

```bash
cd /workspace/robot_assistant_release_20260509
export FLASHRT_ROOT=/workspace/FlashRT
export PI05_BACKEND=flashrt_m50_compat
export M50_DEVICE_ID=0
./run_flashrt_m50.sh
```

Use `./run_flashrt_m50.sh --doctor-only` for resource/device validation, or
`./run_flashrt_m50.sh --agent` for the complete local Qwen3-VL + Pi0.5 loop.

Set `PI05_BACKEND=official` only when comparing against Houmo's original
`HMPI05Policy` path. Both paths consume the same HMM bundle, but the default
control loop now constructs the model through `flash_rt.load_model()`.

## Current limitations

- Only Pi0.5, batch 1, and XH2 device execution are registered.
- The checked-in integration schedules the official six-graph LIBERO bundle;
  DROID or a differently partitioned compilation needs a matching manifest.
- HMM compilation is not performed at model load time. It belongs to the
  Dadao conversion toolchain and normally requires the complete Pi0.5 weights,
  calibration inputs, and a supported GPU conversion environment.
- Device integration tests require the Dadao container and real HMM bundle;
  resource/dispatch tests remain runnable on ordinary development hosts.
